# Dialog Server

Local, stateless Node.js bridge for Arcadia's NPC cognition and dialogue. It listens only on `127.0.0.1:3536`; Godot owns the memory save. Requires Node.js 22+.

## Setup

```bash
cd tools/server
npm ci
cp .env.example .env
npm start
```

On PowerShell use `Copy-Item .env.example .env`.

Set `TYPESAFE_API_KEY` and `OPENAI_API_KEY` in the ignored `.env`, and choose `OPENAI_MODEL`, a Responses API model supporting strict JSON Schema outputs. `TYPESAFE_MODEL` defaults to `jev-latest`. No keys are stored in Godot resources. The server starts without keys but inference endpoints return 503 until configured.

The previous account-specific stored prompt is replaced by the versioned, universal cognitive prompt in `src/dialogue.js`. No remote prompt editing is required. `store: false` remains enabled.

## Flow

1. Godot builds a consumer context (identity, voice, activity, perceptions, relationship, recalls) and calls `POST /v2/dialogue/chat` with the player's message and recent dialogue.
2. The route runs the typed player-speech judgments through the official TypeSafe SDK (`POST https://api.typesafe.ai/v1/systemone`). The questions and tunable thresholds are together in `src/npc-decisions.js`; `speechPolicy` turns the validated answers into the policy the reply is generated under.
3. The reply is generated by OpenAI under that policy, with recalled memories supplied only when the retrieval gate admits them, then its memory proposals are grounded in a separate judgment call. The response returns the typed `judgments`, the reply, grounded `memory_writes` and the IDs of used memories.
4. Godot applies its own relationship dispositions, commits only a valid result for the still-current conversation, then saves locally.

All human NPC resources enable free-text chat. Jev assesses `should_end_conversation` independently of the main interaction intent, so a promise or threat can also be a farewell. At probability 0.8 or higher, code sets `policy.end_conversation`; ambiguous or quoted farewells should keep the conversation open. OpenAI receives that policy to write a short farewell. Godot accepts the exit only after a successful exchange and closes 1.5 seconds after the final page finishes revealing (or when the player advances it). Chat input stays hidden during the farewell. Cancellation, failed requests and reopening clear the pending exit.

Provider failures return 503 errors; malformed requests return 400. They never silently substitute a different decision model. The game shows its fallback dialogue and makes no memory/relationship changes on failure.

Spontaneous and NPC-to-NPC speech is two steps. The game appraises perception and decides whether and how to speak with the cognition routes (`appraise`, then `utterance`; see below). Only an admitted utterance reaches `POST /v2/dialogue/say`, which writes one line in the NPC's saved voice and makes no decisions. See [NPC perception](../../docs/npc_perception.md) for tuning and runtime debugging.

The v1 routes `POST /decide`, `/chat`, `/react`, `/observe` and `/life/*` are removed and return 404; `/v2/cognition/*` and `/v2/dialogue/*` are the only routes.

## Provider queue and upstream budgets

All upstream calls go through one queue (`src/provider-queue.js`) with fixed concurrency: at most 4 judgment calls (TypeSafe) and 2 text calls (OpenAI) run at once; extra work waits in FIFO order. Dialogue grounding runs nested inside the `/chat` text permit with its own judgment permit, so a saturated queue cannot deadlock a chat. Each request carries an `AbortSignal` that fires when the client disconnects: a queued job is dropped without reaching the provider, and an in-flight call is aborted and its permit freed even if the transport never settles. SDK retries are disabled (`maxRetries: 0`); the game decides whether to retry.

Upstream budgets (`src/upstream.js`, exported as `UPSTREAM_BUDGETS_MS`) are aligned with the game's HTTP deadlines (`GAME_DEADLINES_MS`), which each leave a 2000 ms margin (`GAME_DEADLINE_MARGIN_MS`) for transport:

| Call | Server upstream budget | Game deadline |
| --- | --- | --- |
| Judgment: all `/v2/cognition/*`, `/v2/dialogue/chat` judgments | 8000 ms | 10000 ms |
| Dialogue: `/v2/dialogue/chat` generation | 30000 ms | 40000 ms (covers dialogue + grounding + margin) |
| Grounding: `/v2/dialogue/chat` memory-proposal check | 5000 ms | inside the dialogue deadline |
| Ambient text: `/v2/dialogue/say` | 10000 ms | 12000 ms |

## Cognition v2 routes

`POST /v2/cognition/{appraise,select-goal,social,listen,utterance}` (`src/cognition-routes.js`, `src/cognition-contract.js`) return validated typed judgments only; they never apply relationship, memory or goal effects. Requests use `protocol_version: 2` and `prompt_version: "cognition-1"`; any other value returns `409 {error: "protocol_mismatch", protocol_version, prompt_version}` before other validation. The envelope carries `request_id`, `npc_id`, `kind` (must match the route), an opaque `ticket` echoed by the game, a bounded `state`, `evidence` (max 8 items), and the per-kind lists `subjects`, `candidates`, `topics`/`tones` or `intents`. Question ids are generated server-side only from the validated ids.

Statuses: 200 `{request_id, kind, protocol_version, prompt_version, model, judgments}`; 400 `{error: "invalid_request", code}`; 409 protocol mismatch; 413 `payload_too_large`; 502 `{error: "invalid_provider_payload"}` when the provider answer breaks the contract (wrong type, out-of-range score or probability, unknown choice, missing or foreign question); 503 `{error: "unavailable"}` on provider failure or missing keys. Judgments are validated atomically: one bad answer rejects the whole response and unknown fields are dropped.

Request/response examples live in `tests/fixtures/cognition_contract/` (`manifest.json` lists them): `{appraise,select_goal,social,listen,utterance}.{request,response}.json` and the invalid provider answers `invalid_{wrong_type,score_out_of_range,unknown_choice,missing_question,foreign_candidate}.json`. The Node tests and the Godot decision service share them.

## Dialogue v2 routes

`POST /v2/dialogue/say` and `POST /v2/dialogue/chat` (`src/dialogue-routes.js`, `src/dialogue-contract.js`) generate spoken lines. They use the same envelope as the cognition routes (`protocol_version: 2`, `prompt_version: "cognition-1"`, `request_id`, `npc_id`, `npc: {id, profile}`, `context`) and the same status rules: 400 `{error: "invalid_request", code}`, 409 protocol mismatch, 413, 502 `{error: "invalid_provider_payload", code}` for an invalid provider answer, 503 `{error: "unavailable"}`. They never apply relationship, memory or goal effects; the game does.

- `say`: adds `intent` (closed set: `remark, warn, call_for_help, protest, grieve, share, reply, small_talk, report, acknowledge, request_help, decline, farewell`; `share` and `reply` require `topic`), optional `topic` (string or object), `event {text, sense: sight|hearing|touch, player_involved}` and `listener {id, name}`. Returns 200 `{protocol_version: 2, request_id, response}`. One text call with the 10000 ms ambient budget; the line is at most 160 characters and 25 words.
- `chat`: adds `player {message, identity}`, `recent_dialogue [{speaker: player|npc, text}]` and `memories` (candidate memories with ids; fresh perceived events are read from `context.recent_events`). The route runs the player-speech judgments (interaction intent, farewell `should_end_conversation`, `should_remember`, `memory_importance`, `emotional_intensity`, `should_retrieve_memories`, `should_update_belief`, `response_mode` and the five disposition directions) in the judgment pool, applies the thresholds, then generates the reply under a text permit (30000 ms maximum, shortened by the time the judgments took so the route fits the 40000 ms game deadline with its 5000 ms nested memory grounding). Memory candidates reach the model only when the retrieval gate passes. Returns 200 `{protocol_version: 2, request_id, judgments, response, memory_writes, recalled_memory_ids}`; `judgments` are the validated typed answers and no relationship deltas are computed.

Both routes normalize typographic quotes to ASCII, replace em dashes, enforce the length caps and the anti-assistant rules (no offers of help, stock reassurance, summaries or meta commentary). The prompt forbids completed actions, new culprits, unsupported promises and hidden knowledge; the validator additionally rejects (502 `unsupplied_name`) a line that names a resident not present anywhere in the supplied `npc`, `context`, `player`, `recent_dialogue`, `memories`, `event`, `topic` or `listener`. A client disconnect aborts every upstream call and frees its permits. Fixtures: `tests/fixtures/cognition_contract/dialogue_{say,chat}.{request,response}.json`, listed under `dialogue` in `manifest.json`.

## Validation without API access

See [Town life](../../docs/town_life.md) for ownership, persistence, provenance and debugging of the town simulation; its NPC-to-NPC speech arrives here as `/v2/dialogue/say`. Restart the server after updating routes.

```bash
npm test
GODOT=/Applications/Godot.app/Contents/MacOS/Godot npm test
```

The second command also runs a real Godot HTTP exchange against the in-process mock server: player dialogue through `/v2/dialogue/chat`, a v2 `appraise` and `utterance` judgment through `NpcDecisionService`, and `/v2/dialogue/say`. All inference is mocked, including the official SDK transport test; no API credentials or paid requests are used. The HTTP integration test is explicitly skipped when `GODOT` is unset.

## Provider evaluation

`evaluation/cognition-cases.json` is a labeled corpus (52 cases, `prompt_version: "cognition-1"`) over all seven kinds: appraise, select_goal, social, listen, utterance, `dialogue_chat` and `dialogue_say`. Every request is validated by the route's own contract code, and every primary case has a paired counterexample that flips one decisive fact (armed attack vs. routine sparring, bad-news messenger vs. implicated speaker, hungry vs. fed, farewell vs. "before I go" ...). Labels are expected judgment ranges or choices per question id, score orderings, speech-policy outcomes for chat, and text constraints (reference line, word limits, forbidden/required patterns) for generated lines.

`evaluate-cognition.js` runs the cases through the real routes in an in-process app and prints a pass rate per kind:

```bash
npm run evaluate -- --mock                       # offline; a deterministic fake answers with the labels (used by tests)
npm run evaluate -- --mock --kind listen         # or --case appraise.noon_bell
npm run evaluate -- --live --limit 8             # prints the request estimate, then refuses without --yes
npm run evaluate -- --live --limit 8 --yes       # spends real provider requests
```

`--live` is opt-in: it refuses (exit 2) without an explicit `--limit N` (cases are taken round-robin across kinds), without `TYPESAFE_API_KEY` (plus `OPENAI_API_KEY` and `OPENAI_MODEL` when text cases are selected; `.env` is read), and without `--yes`. Before executing it prints the case count, the estimated TypeSafe and OpenAI request counts and the worst-case duration; cost is not estimated. Results (model ids, `prompt_version`, timestamp, per-case output and failures) are written to `evaluation/results/` (gitignored); `--out file` also stores a mock run. Exit codes: 0 all labels passed, 1 a label failed, 2 refused or bad usage. `npm test` covers the corpus validation, the mock run, wrong-answer detection and the live refusals without any network access.

See [NPC memory](../../docs/npc_memory.md) for authoring, persistence and tuning. Live model quality and thresholds still need evaluation on actual game dialogue after credentials are configured.
